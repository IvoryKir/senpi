### Fixed
- Every provider error body is redacted where it enters the provider stream, and an error the provider throws instead of streaming is redacted and classified the same way (a model configuration error is classified on the raw body first), so no partial, `message_start`/`message_update`/`message_end` event, RPC or `--mode json` stream, session file or log line carries it. Redaction is by value: any token-like run after a name whose last part is a credential word (`api_key`, `x-api-key`, `access_token`, `sessionToken`, `client_secret`, `password`, `sig`; any case or separator) in a header, JSON (nested, escaped, doubly escaped, arrays), Go header map, Python repr, XML, URL query or form body, with ASCII, typographic or HTML-escaped quotes and a full-width colon; every field of an object held under such a name; every cookie value; URL userinfo passwords; bearer tokens; and `sk-`, `sk-ant-`, `sk_live_`/`rk_live_`, `gsk_`, `xai-`, `hf_`, Slack `xoxb-`, GitHub, AWS, Google `AIza` keys and JWTs anywhere. Names that only contain a credential word (`primary_key_column`, `token_type`, `max_tokens`, `session_id`, `monkey`) stay readable, and redaction is linear in the body length; `fallback.log` uses the same rules ([#4283](https://github.com/code-yeongyu/senpi/pull/4283))
- A provider or gateway answering that it does not serve the configured model (`model_not_found`, OpenAI's "The model `<id>` does not exist", `unknown provider for model`, Anthropic's `not_found_error` naming the model, or Google's `models/<id> is not found`) no longer retries or walks the fallback chain onto another provider, whatever HTTP status wraps it (a 502 or 503 included): the turn fails with the redacted provider body, `errorCause: { type: "model_config" }`, and one `model_config_error` session event and fallback-log line per model and session. On a model the session already fell back to, the turn ends there instead of trying the next rung ([#4283](https://github.com/code-yeongyu/senpi/pull/4283))

## 2026-10-25 - model_not_found is a configuration error, never a fallback (senpi#4282)

### What changed

- `packages/coding-agent/src/core/agent-session.ts`: `_isRetryableError` and `_isHardErrorFallbackEligible` exclude a message whose typed cause is `model_config` (set by the provider stream from the raw body, whatever status wraps it; never re-tested on the redacted text), and the turn is marked `errorCause: { type: "model_config", model }`, and reported once per model and session as a `model_config_error` session event and a `fallback.log` warning. `AgentSessionEvent` gains `model_config_error`. A configuration error on a model the session already fell back to ends the turn too: no rung after it is tried.
- `packages/coding-agent/src/core/sensitive-output.ts`: `redactSecrets` composes the session's own rules with pi-ai's value-based `redactSecrets`; `retry-fallback/log.ts` uses it for every log string. The environment-assignment rule in `redactSensitiveOutput` matches one bounded name class up to `=` and checks the credential word in a callback (same names redacted), so a long name run is linear instead of quadratic.

### Why

- A gateway that stopped serving a configured model answered `400 model_not_found` for every rung; the hard-error walk silently finished the turn on another provider's model, so work that needed that model family ran on a different one with only a log line to show for it.

### Why an extension could not handle it

- Retry and fallback eligibility is decided inside `AgentSession` before any extension sees the failed turn.

### Expected merge conflict zones

- LOW: the `_isRetryableError` and `_isHardErrorFallbackEligible` predicate lists, the `message_end` pre-queue block, and the not-handled block after the retry decision in `agent-session.ts`; one line in the `AgentSessionEvent` union.

## 2026-10-26 - Provider error bodies are classified raw and kept redacted at the stream boundary (senpi#4282)

### What changed

- `provider-error.ts` (new): `isModelConfigError`, value-based `redactSecrets`, and `sanitizeProviderErrorMessage`, which classifies the raw `errorMessage` of an error message (`stopReason: "error"`) first, sets `errorCause: { type: "model_config", model }` when it names a model the route does not serve, then keeps only the redacted text of every provider error. `redactSecrets` reads a name only from the start of its run of name characters (at most 128), decides by the name's last component (split on `_`, `-`, `.` and camelCase), and bounds every separator quantifier, so it is linear in the input; cookie values, objects under a credential name, XML elements, URL userinfo and the `sk_live_`/`rk_live_`, `gsk_`, `xai-`, `hf_`, `xoxb-` prefixes have their own bounded rules.
- `event-stream.ts`: `AssistantMessageEventStream.push` and `end` run `sanitizeProviderErrorMessage` on every partial, error and final message, so no consumer of any provider stream sees a raw provider error body.
- `retry.ts`: `isRetryableAssistantError` returns false for a `model_config` cause.

### Why

- A redaction applied at `message_end` left the raw body in `message_start`/`message_update` events published before it; every provider builds its error through this stream, so it is the one place where the body enters our objects.
- The previous name pattern allowed unbounded name characters on both sides of the keyword, so one long run that repeated a keyword was quadratic (48 KB of `key` took about 0.8 s, 1 MB minutes), synchronously inside `push`; it also mangled names that only contain a credential word and missed cookie pairs after a short first value.

### Why an extension could not handle it

- The provider stream class and the retry classifier are core pi-ai code that every provider and the agent loop share.

### Expected merge conflict zones

- LOW: the `AssistantMessageEventStream` class body in `event-stream.ts`; the top of `isRetryableAssistantError`.

## 2026-10-26 - Thrown provider errors pass the provider error boundary (senpi#4282)

### What changed

- `packages/agent/src/assistant-terminal-state.ts`: `createTerminalFailureAssistantMessage` runs pi-ai's `sanitizeProviderErrorMessage` on the message it builds from a thrown error, so the terminal message is classified (`errorCause: { type: "model_config" }`) and redacted before `message_start`/`message_end`.
- `packages/agent/src/agent.ts`: `handleRunFailure` runs `sanitizeProviderErrorMessage` on the failure message of a run that threw between turns.

### Why

- An error the stream function throws, or one that fails the run between turns, never passes `AssistantMessageEventStream`: its raw text reached every event and the session file, and a thrown `404 model_not_found` lost its classification, so the session retried it and walked the fallback chain onto another model.

### Why an extension could not handle it

- Both messages are built inside the agent loop and published to every subscriber before an extension sees them.

### Expected merge conflict zones

- LOW: the end of `createTerminalFailureAssistantMessage`; the two lines before the first `processEvents` call in `handleRunFailure` and the `pi-ai` import block of `agent.ts`.
