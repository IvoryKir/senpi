## 2026-10-26 - Tool execution behind one ToolHost boundary (senpi#4360, brain/hand split step 1)

### What changed

- `packages/agent/src/types.ts`: new `ToolHost`, the serializable `ToolHostCall` (`toolCallId`, `toolName`, `args`) and the in-process-only `LocalToolBinding` (`tool`). `AgentLoopConfig.toolHost` is optional.
- `packages/agent/src/agent-loop.ts`:
  - `executePreparedToolCall` hands the prepared, validated call to `toolHost.execute(call, signal, onUpdate, { tool })` instead of calling `tool.execute` itself;
  - the sequential batch, the parallel batch and `runToolCall` (`RunToolCallOptions.toolHost`) all pass the host;
  - `localToolHost` (exported) is the default and runs `tool.execute` in-process, as before. A call without the in-process tool is refused.
- `packages/agent/src/agent.ts`: `AgentOptions.toolHost` / `Agent.toolHost` is passed into the loop config.
- `packages/coding-agent/src/core/agent-session.ts`: nested (subagent) `runToolCall` uses the agent's `toolHost`.
- The loop keeps name resolution, argument preparation, schema validation, the before/after hooks, events and abort handling.
- Still calling `tool.execute` directly (step 2 of the split): `AgentSession.executeTool` (eval and kernel host tools), the Cursor exec bridge (`cursor-exec-bridge.ts`), and the harness tool path (`harness/execution/tools.ts`, a separate tool type).

### Why

- Q (2026-10-26): senpi's brain (the agent loop) and its hands (tool execution) must be separated, with one clean boundary, fusable in one process (the default) and runnable apart. The call record is serializable so a later out-of-process or relay hand implements the same interface. No behaviour change for existing callers.

### Why an extension could not handle it

- Extensions register tools; they cannot replace the loop's own execution step for every tool.

### Expected merge conflict zones

- LOW: `agent-loop.ts` `executePreparedToolCall` and its three call sites; `agent.ts` loop-config assembly.
