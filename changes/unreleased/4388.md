## 2026-10-26 - A linked git worktree inherits its main checkout's project trust (senpi#4388)

### What changed

- `packages/coding-agent/src/core/trust-manager.ts`: `findNearestTrustEntry` still walks `cwd` and its ancestors first; only when none of them has a saved decision and `cwd` is inside a linked git worktree, it repeats the walk from the matching folder of the main checkout. The new `linkedWorktreeMainCheckoutPath` reads the `.git` pointer file, the admin dir's `commondir` and `gitdir` back-pointer, and accepts only a common dir named `.git` that is the main checkout's own `.git` directory; no git is spawned and any unreadable or mismatched layout keeps today's lookup.

### Why

- `packages/coding-agent/src/core/trust-manager.ts`: tools that run one agent per worktree (Orca's `~/orca/workspaces/<repo>/<name>`) create the worktree outside the main checkout, so every new worktree of a trusted repository stopped at "Trust project folder?" before its first turn; in Orca the dialog is not visible in the pane, so `worktree create --agent pi --prompt` looked hung.

### Why an extension could not handle it

- `packages/coding-agent/src/core/trust-manager.ts`: an extension can answer the `project_trust` event, but only `resolveProjectTrusted` consults it; the Full access sync in `agent-session-runtime.ts` and the `--help` fast path read `ProjectTrustStore.get` directly, so a decision inherited only through an extension would be invisible to them, and every user would need that extension for a fact about git's own layout. The inheritance has to live in the store lookup.

### Expected merge conflict zones

- LOW: the `findNearestTrustEntry` body and the `node:fs`/`node:path` import lines in `trust-manager.ts`.
